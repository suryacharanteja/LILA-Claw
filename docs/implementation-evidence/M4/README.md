# M4 browser execution — in progress

Entry follows the approved M2 dependency for W04.1. M3 remains open for factual-label review and provider qualification; no M3 exit approval is inferred. This is Phase 1 work.

Initial increment adds a pure coordinator-side BrowserAction validator against the unchanged approved v1 schema. It checks trusted run/generation/account/tab/origin/adapter/payload context, connection and expiry, exact tool argument sets, unique nonempty field values, and form fingerprint matching for mutations. Tests exercise valid context and rejection of mismatches, expired commands, arbitrary evaluation tools and malformed field arguments.

This validator is not wired into a browser dispatcher yet and grants no authority by itself. No browser command is sent. The extension entry point is still a scaffold; production status remains execution unavailable. No live LinkedIn or provider calls occurred.

Authenticated capability reporting is now accepted by the existing extension socket after session proof. Reports contain protocol version, a bounded allowlisted tool list and bounded adapter identifiers. Unknown fields, duplicate entries, arbitrary evaluation tools, invalid identifiers and unsupported versions are rejected. Reports are scoped to the socket's authenticated session and cleared on renewal/disconnect; status reports whether capabilities were received but continues to state execution unavailable. Tests cover reporting after authentication, rejection before authentication, clearing on renewal and revocation. Reports are self-declared compatibility information, not validated adapter qualification or action authority. The production extension client still needs implementation.

The first full regression for capability reporting exposed a coordinator startup timing failure: missing/busy control-pipe expiry raised pywintypes.error, which bypassed the supervisor's OSError/RuntimeError handling. The pipe client now normalizes only those pre-send readiness expiries to TimeoutError, allowing the existing bounded supervisor startup loop to continue. Deterministic tests cover missing and busy pipes and ensure permission-denied errors still propagate. No command is resent after transmission. The latest summary records the rerun outcome.

The TypeScript extension now exports a tested capability-report builder and session-bound exchange component. It sends only after its caller has verified the server session proof, waits for an exact acknowledgement, rejects old-session replies, and resets on disconnect/send failure. Acceptance cannot set executionReady=true. Five Node tests exercise these rules using the locked TypeScript compiler and no extra dependencies. This is a component, not a completed socket/proof-verification client; the service worker does not open a connection or advertise implemented browser handlers yet. The M4 evidence runner includes the Node results and extension source hashes.

The session-proof component implements the approved length-prefixed reconnect transcript, fresh 32-byte client nonce, HMAC-SHA256 proof and pinned Ed25519 verification over SHA256(transcript + proof). Secret byte buffers are cleared after nonextractable key import; this does not claim secure erasure of caller-owned JavaScript strings. Signature verification is one-use, including failed attempts. Three additional Node tests compare HMAC with an independent server-side implementation, verify signatures, reject cross-handshake replay and reject malformed key encodings. Actual Python-server/Chrome interoperability, secure credential storage and WebSocket integration are still pending; no connected authentication client is claimed.

Subsequent connection increment joins proof verification and capability exchange in an exported ExtensionConnection client. Its default transport is WebSocket to the configured loopback WSS port with no URL credentials. Incoming messages are serialized, size-limited and phase-checked; asynchronous replies are fenced by connection generation. Tests with an injected socket verify authenticated capability reporting, forged proof rejection and disconnected-generation rejection. It advertises empty tool/adapter lists because no handlers are qualified. The extension entry point exports the client but does not instantiate it: setup/credential storage, renewal/reconnect scheduling, build/manifest packaging and actual Chrome/Python interoperability remain unfinished. Browser execution remains unavailable.

Remaining: connect the validator to the authenticated command path; implement extension pairing/session client and strict receive validation; selected-tab inspections and capability exchange; semantic adapters/fingerprints; upload capability handling; receipts and outcome reconciliation; all tool positive/negative fixtures and integrated crash tests. Real-site qualification requires the authorized account/variant testing described in the LLD. M5 is still the first planned integrated business UAT handoff.
